# 앱 보안 점검 (2026-09-06)

학기 일정표([`docs/plan/schedule.md`](../plan/schedule.md))의 9월 행이 보안 취약점 점검을 약속한다. 그때까지 이 저장소의 보안 관련 작업은 화면 단위로 흩어져 있었고([#41](https://github.com/Team-CareerCompass/CareerCompass-FE/issues/41)·[#50](https://github.com/Team-CareerCompass/CareerCompass-FE/issues/50)), 앱 전체를 한 번 훑은 적이 없었다. 이 문서가 그 기록이다.

점검 대상은 `develop` 의 69db375 이고, 백업 경로는 같은 날 35cbfec 에서 한 번 더 봤다. GitHub Actions 공급망은 별도 문서([`actions-supply-chain.md`](actions-supply-chain.md))가 다룬다.

## 고친 것

### 원문 보기가 서버가 준 주소를 스킴 검증 없이 열었다

`PostingRawScreen` 은 공고 상세의 `url` 을 그대로 `Intent.ACTION_VIEW` 에 넘겼다. 이 값은 서버가 준 것이지만 그 서버도 사용자가 등록한 게시판을 크롤러로 긁어 채운다. 게시판 쪽에서 심은 문자열이 앱까지 그대로 온다는 뜻이다. `ACTION_VIEW` 는 스킴에 따라 브라우저가 아니라 다른 앱의 딥링크를 여니, 원문 보기 버튼이 무엇을 열지 서버가 정하게 된다. 도메인 모델의 불변식도 `url` 이 비지 않았는지만 봤다.

`core:common` 에 `ExternalUrl` 을 두고 `http`·`https` 와 호스트가 있는 주소만 통과시킨다. 스킴이 없는 값은 보완하지 않고 거절한다. 서버 값에 앱이 스킴을 붙여 주면 무엇을 열지 앱이 추측하는 셈이다. 거절한 경우 사용자에게는 열기 실패와 같은 안내를 보이고, 계약 위반이므로 리포팅에는 결함으로 남긴다. 주소 전체가 아니라 스킴만 싣는다.

사용자가 입력하는 게시판 주소는 이전부터 `feature:feed:domain` 의 `BoardUrl` 이 같은 두 스킴으로 잠가 왔다. 이번에 서버가 주는 값 쪽이 같은 기준을 갖게 됐다.

### allowBackup="false" 가 기기 간 전송까지 막지는 않았다

이 문서의 첫 판에서 백업을 「차단」으로 적었는데 틀렸다. Android 12(API 31) 이상에서 `android:allowBackup="false"` 는 클라우드 백업만 끄고, [문서](https://developer.android.com/identity/data/autobackup)가 적어 두었듯 일부 제조사 기기에서는 기기 간 전송(D2D)이 그대로 열려 있다. 게다가 `<device-transfer>` 규칙이 없으면 그 모드는 `no-backup`·`cache` 를 뺀 전부가 허용이다. 매니페스트는 규칙 파일을 가리키지도 않았고, `res/xml` 의 두 파일은 안이 빈 안드로이드 스튜디오 템플릿 그대로였다.

즉 기기를 바꾸면 세션 토큰(`datastore/`), 카카오 SDK 가 자체 저장소에 두는 토큰, 그 기기에서만 뜻이 있는 지문 로그인 등록 플래그가 새 기기로 따라갈 수 있었다.

그중 카카오 SDK 토큰은 백업 경로와 별개로 로그아웃 뒤에도 기기에 남아 있었다([#370](https://github.com/Team-CareerCompass/CareerCompass-FE/issues/370)). 로그아웃이 서버 세션 종료와 앱 저장소 정리만 했기 때문인데, 소셜 로그인 요청이 그 SDK 토큰 하나만 받으므로 남은 토큰으로 서버 세션을 다시 열 수 있었다. 지금은 세션이 끝나는 자리 둘, 즉 로그아웃과 재발급 거절에 따른 세션 정리 모두에서 `SocialSessionCleaner` 가 SDK 토큰을 함께 비운다. SDK 의 `logout` 은 서버 응답이 실패여도 자기 저장소를 비우므로 네트워크가 없어도 기기에서는 지워지고, 앱은 그 응답을 기다리지 않는다.

`data_extraction_rules.xml` 에 두 섹션을 모두 적고 앱 데이터 루트를 통째로 뺐다. 매니페스트가 그 파일을 가리키게 했고, 쓰지 않던 `backup_rules.xml` 은 지웠다. 사용자 데이터의 정본은 서버라 기기에서 옮길 것이 없다.

저장소 정책도 함께 뒤집었다. `verify-android-manifest.mjs` 는 「백업이 꺼져 있으면 `dataExtractionRules` 를 선언하지 말 것」을 강제하고 있었다. 그 규칙이 이 구멍을 박아 두고 있었다. 이제 선언을 요구하고, 규칙 파일이 두 경로 모두에서 전부를 빼는지까지 본다. `fullBackupContent` 는 여전히 금지다. API 30 이하에서는 `allowBackup="false"` 가 전부를 끄기 때문이다.

## 결정한 것

### 토큰은 계속 평문 DataStore 에 둔다 ([#271](https://github.com/Team-CareerCompass/CareerCompass-FE/issues/271))

위협 모델을 이렇게 잡았다. 지키려는 것은 로그인 세션이고, 상대는 기기를 물리적으로 손에 넣은 사람 또는 루팅된 기기의 다른 앱이다. 서버에 있는 자기소개서 본문이 그 세션으로 열린다.

기기가 잠겨 있으면 파일 기반 암호화가 막고, 잠금이 풀린 정상 기기에서는 앱 샌드박스가 막는다. 백업으로 빠져나가는 길은 위에서 닫았다. 남는 것은 루팅된 기기인데, 거기서는 Keystore 로 감싸도 공격자가 앱과 같은 자격으로 키를 부를 수 있어 얻는 것이 크지 않다. 반대로 잃는 것은 분명하다. 키 무효화나 복호화 실패가 곧 로그아웃으로 보이고, 그 실패 경로를 잘못 다루면 멀쩡한 사용자가 튕긴다.

그래서 지금은 바꾸지 않는다. 다시 볼 조건 둘을 못 박아 둔다. 자기소개서 본문이나 과거 지원서를 기기에 저장하기 시작하면, 그리고 Play 정식 출시로 실사용자를 받기 전에 다시 판단한다. 참고로 `androidx.security:security-crypto` 는 유지보수가 끊긴 라이브러리라 그때도 후보가 아니다. 고른다면 Android Keystore 를 직접 쓴다.

### 화면 캡처는 막지 않는다 ([#272](https://github.com/Team-CareerCompass/CareerCompass-FE/issues/272))

`FLAG_SECURE` 를 어느 화면에도 걸지 않는다.

이 앱에서 민감한 화면은 지원서 에디터와 과거 지원서인데, 거기 있는 것은 사용자 본인이 쓴 글이다. 자기소개서는 캡처해서 남에게 보여 주고 피드백을 받는 것이 정상 사용이다. 캡처를 막으면 그 흐름을 앱이 끊는다. 반대로 막아서 얻는 것은 최근 앱 목록 미리보기와 화면 녹화 앱 정도인데, 녹화는 사용자가 직접 권한을 준 경우이고 미리보기는 같은 기기 안에서 본인에게만 보인다.

남의 데이터를 보여 주게 되면 다시 판단한다. 커리어 로드맵의 코호트 비교([#192](https://github.com/Team-CareerCompass/CareerCompass-FE/issues/192))가 표본을 어떻게 보여 주느냐에 따라 그 조건에 걸린다.

- 인증서 고정(`CertificatePinner`)은 쓰지 않는다. 서버 도메인과 인증서가 아직 없어 고정할 대상이 없다. 서버가 서면([BE #7](https://github.com/Team-CareerCompass/CareerCompass-BE/issues/7)) 그때 필요 여부를 판단한다.
