# 실서버 QA 라운드 대본

`BASE_URL` 이 실주소로 바뀐 뒤 처음 한 바퀴를 도는 순서다. 로그인부터 원문 보기까지 단계마다 무엇을 누르고
무엇이 보여야 하는지, 그 손짓이 어느 엔드포인트를 무는지 적었다. 주소를 받은 사람이 이 문서만 들고
순서대로 돌 수 있게 쓴다.

대본이 없으면 그 자리에서 즉흥으로 눌러 보게 되고, 계약이 어긋난 자리를 기록 없이 지나친다. 판정 기준을
주소가 오기 전에 못 박아 두는 것이 이 문서의 값이다.

**표의 따옴표 안 문구는 전부 저장소의 문자열 리소스에서 그대로 옮겼다.** 지어낸 문장은 없다. 리소스 이름을
같이 적었으니 값이 다르면 앱이 바뀐 것이거나 이 문서가 낡은 것이다.

본체는 [#265](https://github.com/Team-CareerCompass/CareerCompass-FE/issues/265) 이고 실주소는
[BE #7](https://github.com/Team-CareerCompass/CareerCompass-BE/issues/7) 의 산출물이다. 이 문서는 그것을
기다리지 않고 미리 정할 수 있는 것만 정한다([#287](https://github.com/Team-CareerCompass/CareerCompass-FE/issues/287)).

## 전제

전제는 여기서 다시 쓰지 않는다. 아래가 정본이다.

| 무엇 | 어디 |
| --- | --- |
| 어느 기기·어느 화면에서 도는가, 기기를 혼자 쓰는가, 증거를 어떻게 남기는가 | [`device-baseline.md`](device-baseline.md) |
| 어느 커밋의 빌드를 돌리는가 | [`device-baseline.md`](device-baseline.md) 의 「앱이 어느 커밋인가」 |
| 화면마다 어떤 상태를 그리는가(오프라인·로딩·빈 결과·점검·세션 만료) | [`../spec/edge-states.md`](../spec/edge-states.md) |
| 서버 에러 코드 14종의 사용자 문구와 행동 | [`../spec/error-copy.md`](../spec/error-copy.md) |
| 정본이 어긋날 때 무엇을 따르는가 | [`../spec/canon.md`](../spec/canon.md) |
| 콜드 스타트 기준값 | [`cold-start-2026-09-03.md`](cold-start-2026-09-03.md) |
| 결과를 공개 대장에 남기는 절차와 스키마 | [`evidence/README.md`](evidence/README.md) |

`device-baseline.md` 가 「앱이 커밋 정보를 들고 있지 않다」고 적어 둔 것은 그 뒤에 해결됐다. debug 빌드의
`versionName` 에 커밋 지문이 붙는다(`1.0+a3f91c2`, 커밋 안 된 변경이 있으면 `1.0+a3f91c2-dirty`,
`build-logic/src/main/kotlin/BuildFingerprint.kt`). 그래서 설치된 앱이 어느 커밋인지는 아래 한 줄로 읽는다.

```bash
adb -s <serial> shell dumpsys package com.cambridge.careercompass_fe | grep versionName
```

## 대본 읽는 법

표의 열은 넷이다.

- 손짓: 누르거나 입력하는 것.
- 보여야 하는 것: 화면에 떠야 하는 값. 따옴표 안은 문자열 리소스 그대로이고 괄호 안이 리소스 이름이다.
- 요청: 그 손짓이 무는 엔드포인트(`core/network/.../service/`). 어긋난 자리를 드리프트 표에 적을 때 이 열을 쓴다.
- 조건: **비어 있으면 지금 앱에서 그대로 유발할 수 있다.** 값이 있으면 서버가 그 상태를 만들어 줘야만 보이거나,
  앱 바깥(소셜 콘솔·기기 설정)의 준비가 필요하다.

조건이 붙은 줄을 돌지 못했으면 라운드 문서의 「확인하지 못한 것」에 사유와 함께 적는다. 통과로 적지 않는다.
조건이 붙은 줄만 모아 둔 표가 아래 [「서버가 만들어 줘야 보이는 것」](#서버가-만들어-줘야-보이는-것)이다.
라운드를 시작하기 전에 그 목록을 서버 쪽에 통째로 넘기면 한 번에 무대를 세울 수 있다.

## 0. 라운드를 시작하기 전에

- [ ] `BASE_URL` 이 실주소인가. 기본값은 자리표시자
      `https://api.careercompass.invalid/api/v1/` 다(`core/network/build.gradle.kts`). 자리표시자로 도는 빌드는
      전송 실패만 재현하므로 이 대본을 돌 수 없다.
- [ ] 주소가 https 인가. 매니페스트가 `android:usesCleartextTraffic="false"` 라 http 주소는 전송 실패로
      떨어지고 화면에는 「연결할 수 없어요」로만 보인다. 계약 문제로 오인하기 쉬운 자리다.
- [ ] 설치된 앱의 `versionName` 접미사가 이번 라운드로 정한 커밋인가. `-dirty` 면 커밋 안 된 변경 위에서
      빌드된 것이라 증거를 그 커밋에 붙일 수 없다.
- [ ] 기기·화면 프로파일을 확정했는가(`./scripts/qa-device-profile.sh status --json`).
- [ ] 계정이 둘 있는가. 로그인 응답의 `isNewUser` 가 온보딩과 피드를 가르므로, 서버가 처음 보는 계정 하나와
      이미 가입된 계정 하나가 필요하다.
- [ ] 카카오·Google 콘솔에 이 빌드의 키 해시·클라이언트 id 가 등록돼 있는가.
- [ ] 수집이 실제로 도는 게시판 URL 을 하나 골라 두었는가. 정적 HTML 목록 페이지여야 한다(§6).

## 1. 로그인

시작 화면은 셸이 고른다. 세션이 없으면 로그인, 지문 등록이 있으면 지문 로그인, 온보딩 도중이면 그 단계다.
판정은 `app/.../session/MainViewModel.kt` 가 하고 `navigation/AppNavigation.kt` 는 그 답을 화면에 붙이기만 한다.

| 손짓 | 보여야 하는 것 | 요청 | 조건 |
| --- | --- | --- | --- |
| 앱을 켠다(세션 없음) | 브랜드 마크와 「CareerCompass」, 「AI가 분석하는 나만의 진로 나침반」(`onboarding_login_tagline`), 「카카오 로그인」·「Google 계정으로 로그인」, 「계속하면 서비스 이용약관과 개인정보 처리방침에 동의하는 것으로 간주돼요」 | 없음 | |
| 「카카오 로그인」 | 카카오 인증으로 나갔다 돌아오고, 돌아온 뒤 「로그인하는 중이에요」(`onboarding_login_loading`)와 잠긴 버튼 | `POST auth/social/kakao`(`accessToken`·`deviceId`·`fcmToken`) | 콘솔에 키 해시 등록 |
| 신규 계정으로 성공 | 온보딩 Step 1 로 이동 | 응답 `isNewUser = true` | 서버가 처음 보는 계정 |
| 기존 계정으로 성공 | 「지문으로 더 빠르게 로그인할까요?」(`onboarding_biometric_enroll_title`) 시트가 한 번. 「나중에 하기」를 누르면 피드 | 응답 `isNewUser = false` | 이미 가입된 계정 |
| 그 시트에서 「지문 등록하기」 | 시스템 지문 프롬프트 뒤 피드 | `POST auth/biometric/register` | 기기에 지문이 등록돼 있어야 한다 |
| 연결을 끊고 로그인 | 하단 오류 카드에 「네트워크 연결을 확인한 뒤 다시 시도해 주세요」(`onboarding_login_failure_network`) | 없음(전송 실패) | |
| 서버가 `AUTH_REQUIRED`·`AUTH_INVALID` 를 준다 | 「로그인에 실패했어요. 다시 시도해 주세요」(`onboarding_login_failure_rejected`) | 위와 같음 | 서버가 그 코드를 주도록 무대를 세워야 한다 |
| 그 밖의 실패 | 「문제가 생겨 로그인하지 못했어요. 잠시 후 다시 시도해 주세요」(`onboarding_login_failure_unknown`) | | 서버 응답 사유에 달렸다 |

지문 로그인 화면은 지문을 등록한 뒤 앱을 다시 켜야 나온다. 「%s님, 안녕하세요」(`onboarding_biometric_greeting`)와
「지문으로 빠른 로그인」이 보이고, 실패 문구 세 가지는 기기 상태가 만든다(`onboarding_biometric_failure_*`).

## 2. 온보딩 Step 1 기본 정보

온보딩에 들어가면 먼저 `GET users/me` 로 재개 지점을 정하고 폼을 프리필한다
(`ResolveOnboardingEntryUseCase`). 조회에 실패해도 진입은 막지 않고 빈 폼으로 시작한다.

| 손짓 | 보여야 하는 것 | 요청 | 조건 |
| --- | --- | --- | --- |
| Step 1 진입 | 「기본 정보를 알려주세요」, 「공고 추천과 자소서 생성에 사용돼요」, `STEP 1 / 4` | `GET users/me` | |
| 재진입(중단했던 계정) | 중단한 단계가 열리고 이미 저장한 값이 채워져 있다 | 위와 같음 | 서버 프로필에 값이 남아 있어야 한다. 단계 쪽은 아래 참조 |
| 이름·학과 입력 | 비우면 「필수 입력이에요」(`onboarding_field_required`) | 없음(로컬 검증) | |

| 졸업 예정에 `1999.03` | 「2000년 이후로 선택해 주세요」 | 없음 | |
| 「다음」 | Step 2 로 이동 | `PATCH users/me` | |
| 저장이 실패한다 | 하단 실패 배너([`../spec/error-copy.md`](../spec/error-copy.md) 의 행 그대로). 「다음」이 다시 눌린다 | 위와 같음 | 서버가 그 코드를 주도록 |

재진입에서 서버가 정하는 것은 프리필 값과 「온보딩을 이미 마쳤나」(`onboardingDone`) 둘뿐이다. **어느 단계로
돌아가는지는 기기 안의 진행 기록이 정한다**(`ResolveOnboardingEntryUseCase` 가 읽는 `OnboardingProgressRepository`).
그래서 앱을 지우고 다시 깔거나 다른 기기로 옮기면 서버에 값이 남아 있어도 Step 1 부터 시작한다. 재개를 볼 때는
같은 기기에서 앱을 껐다 켜는 쪽으로 돌고, 재설치 뒤 Step 1 로 가는 것은 결함이 아니다.

## 5. 온보딩 Step 4 과거 지원서와 완료

| 손짓 | 보여야 하는 것 | 요청 | 조건 |
| --- | --- | --- | --- |
| Step 4 진입 | 「과거 지원서가 있다면 올려주세요」, 「파일을 드래그하거나 탭하세요」, 「PDF · DOCX · TXT · 최대 10MB」 | `GET past-applications` | |
| PDF 를 고른다 | 카드가 생기고 상태 줄에 「분류 중」(`onboarding_step4_document_processing`) | `POST past-applications/upload`(multipart, `file`·`label`) | |
| 업로드 응답이 온다 | 「분류 완료 · N개 항목」(`onboarding_step4_document_completed`) | 위 응답의 `items` | **분류 결과가 업로드 응답에 실려 와야 한다.** 앱은 이 뒤로 다시 묻지 않는다 |
| 항목을 펼쳐 분류를 바꾼다 | 고른 분류로 바뀐다 | `PATCH past-applications/{appId}/items/{itemId}` | 응답에 `items` 가 하나 이상 있어야 한다 |
| 10MB 넘는 파일 | 「파일은 10MB 이하만 올릴 수 있어요」 | 없음(로컬 검증) | |
| PNG 파일 | 「PDF, DOCX, TXT 파일만 올릴 수 있어요」 | 없음 | |
| 업로드가 실패한다 | 카드 상태 줄이 「연결 실패 · 재시도」 꼴로 바뀐다(`onboarding_upload_failed_*`) | 위와 같음 | 사유별로 서버가 만들어 줘야 한다 |
| 「건너뛰기」 또는 「완료」 | 「프로필 완성!」, 「%s님, 이제 딱 맞는 공고를 찾아드릴게요」, 「공고 보러 가기」·「게시판 먼저 등록하기」 | `GET users/me`(best-effort) | 이름은 프로필에 있을 때만. 없으면 이름 없는 문구 |

**화면에 둔 채로는 「분류 중」이 스스로 풀리지 않는다.** 업로드 요청이 응답할 때 카드 상태가 바뀌고, 앱은
그 뒤로 분류 상태를 다시 묻지 않는다(`OnboardingViewModel.upload`). 서버가 업로드를 먼저 받고 분류를 나중에
끝내는 구조라면 그 카드는 화면을 떠날 때까지 「분류 중」에 머문다. Step 4 를 나갔다 다시 들어오면 그때 한 번
`GET past-applications` 를 다시 읽어 분류가 반영되므로(`loadPastApplications`), 두 번 다 확인해 어느 쪽인지
가른다. 다시 들어와서 풀린다면 계약의 문제이고, 다시 들어와도 안 풀린다면 서버가 아직 분류하지 못한 것이다.
어느 쪽이든 화면에 둔 채 풀리지 않는 것은 드리프트가 아니라 결함이므로 이슈로 낸다.

완료 화면의 「게시판 먼저 등록하기」는 피드 host 로 옮긴 뒤 게시판 등록을 스택에 쌓는다. 「공고 보러 가기」는
피드 홈으로 가는데, 그 길목에 §1 과 같은 지문 등록 시트가 한 번 낀다(`BiometricEnrollGate`). 신규 계정으로
도는 라운드에서는 여기서 시트를 보게 되므로 §1 의 시트와 같은 것으로 세지 않는다. 「게시판 먼저 등록하기」는
묻지 않고 그대로 보낸다.

## 6. 게시판 등록

들어가는 길은 둘이다. 온보딩 완료의 「게시판 먼저 등록하기」와, 피드가 비었을 때 뜨는 「게시판 등록하기」다.

| 손짓 | 보여야 하는 것 | 요청 | 조건 |
| --- | --- | --- | --- |
| 진입 | 「게시판 등록」, 「AI가 사이트 구조를 자동 분석」, 「게시판 URL *」 | 없음 | |
| URL 을 넣고 「구조 분석하기」 | 「게시글 구조를 분석하고 있어요」와 「사이트 응답 속도에 따라 1분 넘게 걸릴 수 있어요」 | `POST boards/detect`(`url`) | |
| 감지 성공 | 「감지 성공 · 최근 게시글 N개」와 미리보기 목록 | 응답 `detectStatus`·`preview` | 서버가 실제로 그 사이트를 긁어야 한다 |
| 날짜를 못 찾은 감지 | 「날짜를 찾지 못해 마감일 파싱 정확도가 낮을 수 있어요」 | 미리보기의 `date` 가 비었을 때 | 날짜 규칙이 없는 게시판이 필요하다 |
| 로그인이 필요한 게시판 | 「로그인이 필요한 게시판은 지원하지 않습니다」 | `detectStatus` 가 그 값일 때 | 서버가 그 상태를 판정해 줘야 한다 |
| JavaScript 로 그리는 게시판 | 「JavaScript 로 그려지는 게시판이라 자동 감지에 실패했어요. 수동 등록을 문의해 주세요」 | 위와 같음 | 위와 같음 |
| 수집을 막아 둔 사이트 | 「해당 사이트는 자동 수집이 허용되지 않습니다」 | 위와 같음 | 위와 같음 |
| 구조를 못 찾은 사이트 | 「게시글 구조를 찾지 못했어요. 목록 페이지 주소인지 확인해 주세요」 | 위와 같음 | 위와 같음 |
| 감지가 아주 오래 걸린다 | 「분석이 오래 걸려 멈췄어요」 상자와 「다시 시도」 | 타임아웃 | 응답이 늦는 사이트가 필요하다 |
| 이름·유형·주기를 정하고 「등록하기」 | 「게시판을 등록하고 있어요」, 「끝나면 게시판 목록으로 돌아가요」 뒤에 앞 화면으로 | `GET boards` 로 상한 확인 뒤 `POST boards` | |
| 등록 중 뒤로 가기 | 「등록을 끝내는 중이에요. 잠시만 기다려 주세요」 스낵바. 화면이 닫히지 않는다 | | |
| 같은 URL 을 다시 등록 | 「이미 등록된 게시판이에요」 | 서버 `DUPLICATE_BOARD` | 서버가 중복을 판정해야 한다 |
| 21번째 게시판 | 「게시판을 더 등록할 수 없어요」와 「최대 20개까지 등록할 수 있어요」 | `GET boards` 만. `POST boards` 는 보내지 않는다(`MAX_BOARDS = 20`) | 게시판 20개를 미리 만들어야 한다 |

수집 주기 선택지는 셋이다. 「1일 1회」(24시간), 「1일 2회」(12시간), 「주 1회」(168시간). 고른 값이
`cycleHours` 로 나간다.

## 7. 수집 대기

등록 직후에는 공고가 없다. **이 구간에서 앱이 보여 줄 수 있는 것은 피드 홈의 빈 화면 하나뿐이다.**

| 손짓 | 보여야 하는 것 | 요청 | 조건 |
| --- | --- | --- | --- |
| 등록 직후 피드 홈 | 「아직 모인 공고가 없어요」(`feed_empty_not_collected_title`)와 「등록한 게시판에 새 글이 올라오면 여기에 쌓여요」 | `GET postings` 가 빈 목록 | |
| 같은 화면의 안내 줄 | 「등록한 게시판을 1일 1회 확인하고 있어요」(`feed_empty_collect_notice`) | `GET boards` | |
| 주기가 다른 게시판을 섞어 등록 | 「가장 자주 보는 게시판을 1일 2회 확인하고 있어요」(`feed_empty_collect_notice_mixed`) | 위와 같음 | 주기가 서로 다른 게시판 둘 |
| 등록한 게시판을 전부 꺼 둔다 | 안내 줄이 사라진다(꺼 둔 게시판은 세지 않는다) | 위와 같음 | 이번 라운드에서는 만들 수 없다. 끄는 손짓이 게시판 목록 화면에만 있는데 그 화면에 갈 길이 없다(아래 참조) |
| 첫 수집이 끝난 뒤 새로고침 | 공고 목록이 뜬다 | `GET postings` | 서버가 실제로 한 주기를 돌아야 한다 |

안내 줄은 켜져 있는 게시판 중 **가장 짧은 주기**를 말한다(`FeedStateMapping.toCollectNotice`). 주기가 서로
다르면 문구 자체가 「가장 자주 보는 게시판을」로 갈린다.

내 게시판 목록 화면(「내 게시판」, 「마지막 수집 %s」, 「아직 수집 전」, 수집 실패 횟수, 켜고 끄기, 재시도)은
코드에 있지만 **지금 앱에서 그 화면으로 가는 길이 없다.** 화면을 여는 의도(`FeedIntent.RequestBoardList`)를
내는 UI 가 저장소 어디에도 없고 테스트만 그것을 부른다. 그래서 이번 라운드에서 수집 상태를 게시판별로
확인할 방법은 없고, 수집이 돌았는지는 피드 목록이 채워지는 것으로만 판정한다. 라운드에서 이 자리를
「확인하지 못한 것」으로 남기고 진입점 이슈를 따로 낸다.

## 8. 피드

| 손짓 | 보여야 하는 것 | 요청 | 조건 |
| --- | --- | --- | --- |
| 피드 홈 진입 | 「안녕하세요, %s님」, 「오늘 신규 공고 %d건」, 검색칸 「공고 제목·키워드 검색」, 「%d개 공고」 | `GET postings`(`sort`·`limit`) + `GET boards` | 공고가 하나 이상 |
| 이름이 없는 프로필 | 인사말의 이름 자리가 「회원」(`feed_user_name_fallback`) | | 프로필에 이름이 없어야 한다 |

| 프로필이 덜 찬 계정 | 칩이 「프로필 필요」, 목록 위에 「프로필을 입력하면 적합도를 확인할 수 있어요」와 「입력하기」 | | 점수가 없는 공고와, 희망 직무·관심 태그가 둘 다 빈 프로필. 판정은 앱이 한다(§10 참조) |

| 북마크를 누른다 | 칩 상태가 바뀐다. 실패하면 「북마크를 저장하지 못했어요」 | `POST`/`DELETE postings/{id}/bookmark` | |

| 끝까지 스크롤 | 「공고를 더 불러오는 중이에요」 뒤 다음 페이지 | `cursor` 에 앞 응답의 `nextCursor` | 한 페이지를 넘는 공고 수가 필요하다 |
| 검색어를 넣어 결과가 없다 | 커서가 안 남았으면 「‘%s’ 검색 결과가 없어요」와 「검색어 지우기」. 커서가 남았으면 「여기까지는 찾지 못했어요」와 「더 찾아보기」 | | 두 갈래를 다 보려면 여러 페이지 분량의 공고가 필요하다 |
| 연결을 끊고 아래로 당겨 새로고침 | 「연결할 수 없어요」 화면. 저장된 스냅샷이 있으면 「오프라인 모드로 보기」 | | 스냅샷 버튼은 한 번 이상 목록을 받아 둔 뒤에만 |

아무 신호도 없고 순서만 조용히 같다.

## 10. 적합도

상세 화면 안의 카드 하나지만 판정이 여럿이라 절을 따로 둔다. 자동 재조회 간격과 횟수는
`SUITABILITY_AUTO_RECHECK_INTERVAL = 5초`, `SUITABILITY_AUTO_RECHECK_LIMIT = 4회` 다.

| 손짓 | 보여야 하는 것 | 요청 | 조건 |
| --- | --- | --- | --- |
| 분석이 끝난 공고 | 「AI 적합도 분석」, 점수와 `/100`, 등급(「매우 적합」·「적합」·「보통」·「낮음」) | 응답 `suitability` | 분석이 끝난 공고 |
| 축별 점수 | 「분야 유사도」·「자격 조건 충족도」·「우대 조건 매칭」·「경쟁 강도」와 가중치 `%d%%` | `suitability.breakdown` | 서버가 네 축을 채워야 한다 |
| 축이 비어 있다 | 「축별 세부 점수는 아직 없어요」 | `breakdown` 이 빈 배열 | |
| 강점·약점 | 「강점」·「약점」 절 | `strengthComment`·`weaknessComment` | 서버가 문장을 채워야 한다 |
| 분석 전 공고에 들어간다 | 카드 안에 「AI가 분석 중이에요」와 「적합도가 나오면 이 자리에 바로 보여 드릴게요」 | 5초마다 `GET postings/{id}` 를 4회까지 조용히 다시 | 분석 전 공고 |
| 그대로 20초 이상 둔다 | 「아직 적합도가 나오지 않았어요」와 「다시 확인」 버튼. 진행 표시가 사라진다 | 재조회 소진 | 그 사이 분석이 끝나지 않아야 한다 |
| 「다시 확인」 | 한 번 더 묻고, 여전히 없으면 같은 상태로 돌아온다 | `GET postings/{id}` 1회 | |
| 프로필이 덜 찬 계정 | 「프로필을 입력하면 적합도를 확인할 수 있어요」와 「프로필 입력하기」 | | §8 과 같은 조건이고 같은 판정이다 |

「분석 중」과 「프로필 미입력」을 가르는 것은 **앱의 판정**이다(`judgeSuitability`). 점수가 있으면 그대로 보이고,
점수가 없는데 프로필의 희망 직무와 관심 태그가 둘 다 비었으면 「프로필 미입력」, 그 밖은 「분석 중」이다.
`PROFILE_INCOMPLETE` 에러 코드는 이 자리와 무관하다. 그 코드는 실패 화면(`FailureDisplay`)으로 갈 뿐 칩을
바꾸지 않는다. 자동 재조회는 「분석 중」일 때만 돈다. 온보딩 Step 2 가 희망 직무와 태그를 각각 하나 이상
요구하므로 정상으로 가입한 계정은 이 자리에 오지 않는다. 서버가 그 값을 비워 돌려주면 그때 「프로필 미입력」이
뜨므로, 그 응답 모양을 드리프트 표에 남긴다.

등급 경계는 80·60·40 이다(`SuitabilityLabel`). 80 이상이 「매우 적합」, 60 이상이 「적합」, 40 이상이 「보통」,
그 아래가 「낮음」이다. 서버가 `scoreLabel` 을 주면 그것을 쓰고, 모르는 값이거나 없으면 점수에서 다시 계산한다.
그래서 서버와 앱의 경계가 어긋나도 화면에는 신호가 없다. 60점대와 80점대 공고를 하나씩 열어 서버가 준
`scoreLabel` 과 화면의 등급이 같은지 대조한다. 필터의 「60점 이상 (적합)」·「80점 이상 (매우 적합)」도 같은 경계다.

## 11. 원문 보기

| 손짓 | 보여야 하는 것 | 요청 | 조건 |
| --- | --- | --- | --- |
| 상세 하단 「원문 보기」 | 「원문 보기」 화면, 「%s · %s 수집」, 본문 | `GET postings/{id}` 를 다시 | |
| 본문이 비어 있다 | 「본문을 가져오지 못했어요」 | 응답 `rawContent` 가 빈 문자열 | 서버가 본문을 못 긁은 공고가 필요하다 |
| 「원본 링크 열기」 | 브라우저로 나간다 | 없음(응답 `url`) | |

| 조회가 실패한다 | 「원문을 불러오지 못했어요」와 「다시 시도」 | | |

원문 화면은 상세와 같은 엔드포인트를 다시 부른다. 상세에서 본 값과 원문에서 본 값이 다르면 그 사이
서버가 갱신한 것이므로, 다르면 두 시각을 함께 적는다.

## 계약 드리프트 기록

응답이 계약과 다른 자리는 전부 아래 열로 적는다. **한 줄이 한 필드다.** 같은 응답에서 세 필드가 어긋났으면
세 줄이다. 줄을 합치면 나중에 어느 것이 고쳐졌는지 셀 수 없다.

| 열 | 무엇을 적나 | 예 |
| --- | --- | --- |
| 엔드포인트 | 메서드와 경로. 대본의 「요청」 열 값 그대로 | `GET postings` |
| 필드 | 봉투 `data` 안의 경로 | `postings[].collectedAt` |
| 앱이 기대한 것 | DTO 의 이름·타입·nullable. 근거 파일을 함께 | `String` 필수, `PostingDto` |
| 실제로 온 것 | 값 또는 부재를 그대로. 값이 길면 앞 40자 | `"2026-09-08 14:03:00"` |
| 증상 | 화면에서 무엇이 됐나 | 목록 전체가 파싱 실패로 빈다 |
| 판정 | 서버 결함 · 앱 결함 · 계약 미정 셋 중 하나 | 계약 미정 |
| 이슈 | 낸 이슈 번호. 판정이 「계약 미정」이면 양쪽 저장소 모두 | FE #___ / BE #___ |

판정을 셋으로 가르는 기준은 이렇다.

- API_SPEC 이 그 필드를 명시했고 서버가 다르게 주면 서버 결함이다.
- API_SPEC 대로 왔는데 앱이 못 읽으면 앱 결함이다.
- API_SPEC 이 그 자리를 말하지 않았으면 계약 미정이다. 어느 쪽도 틀리지 않았으므로 고칠 곳을 먼저
  합의해야 한다. 이 판정이 나오면 [`../spec/canon.md`](../spec/canon.md) 의 「정본끼리 어긋난 곳」 표에도 줄을 더한다.

자주 어긋나는 자리를 미리 적어 둔다. 라운드에서 이 넷은 값을 못 보고 지나치기 쉽다.

- **날짜와 시각.** 앱은 `dueDate` 를 `2026-05-25` 로, `collectedAt` 을 `2026-05-18T07:00:00+09:00` 또는 `Z` 로
  읽는다(`WireTime`). 형식이 다르면 예외가 나고 화면에는 일반 실패로만 보인다.
- 커서. `nextCursor` 가 없으면 이어 읽기가 멈춘다. 빈 문자열은 앱이 없는 것과 같게 접으니(`PostingRepositoryImpl`)
  그쪽은 안전하고, 위험한 것은 서버가 **같은 커서를 계속 돌려주는 경우**다. 앱은 끝을 모른 채 같은 페이지를
  다시 읽는다. 이어 읽기를 두 번 눌러 목록이 실제로 늘어나는지 본다.
- 열거값. `type`·`scoreLabel`·`status`·`detectStatus`. 모르는 값이 오면 앱은 기본값으로 접고 조용히 넘어간다.
  `type` 은 「기타」, `scoreLabel` 은 점수에서 다시 계산한다. 화면에 신호가 없으니 응답을 직접 봐야 잡힌다.
- 에러 코드. 앱이 아는 것은 14종이다(`ApiFailureMapper`). 그 밖의 코드는 HTTP 상태로만 갈리고, 상태도
  안 맞으면 원인을 특정하지 못한 일반 실패가 된다.

## 라운드 문서 양식

라운드 하나가 문서 하나다. 파일 이름은 `docs/qa/server-round-YYYY-MM-DD.md` 이고, 같은 날 두 번 돌았으면
뒤에 `-2` 를 붙인다. 절 구성은 아래로 고정한다.

1. 환경. 커밋 sha, `versionName` 접미사, `BASE_URL`, 기기와 실효 dp(`qa-device-profile.sh status --json` 출력),
   서버 쪽 담당자와 무대를 세운 시각.
2. 결과 요약. 이 대본의 11개 절을 그대로 열거하고 각각 통과·실패·확인 못 함 중 하나. 실패에는 이슈 번호.
3. 계약 드리프트. 위 표를 그대로.
4. 확인하지 못한 것. 조건이 붙어 있었는데 무대를 못 세운 줄. 사유를 함께 적는다. **비워 두지 않는다.**
   확인 못 한 것이 없으면 「없음」이라고 쓴다.
5. 대본에 없던 것. 돌다가 새로 발견한 화면·경로. 다음 라운드부터 이 대본에 줄을 더한다.

문서를 쓴 뒤 공개 증거 대장에도 남긴다. 절차와 스키마는 [`evidence/README.md`](evidence/README.md) 이고,
파일 이름이 검증한 HEAD 의 전체 sha 다. 라운드 문서는 사람이 읽는 서술이고 대장은 기계가 읽는 기록이라
둘 다 남긴다.

실패마다 이슈를 낸다. 이슈 하나에 실패 하나다. 본문에는 이 대본의 몇 번 절 몇 번째 줄인지와, 그때의 요청과
응답을 적는다.

## 이 대본이 덮지 않는 것

- 초안 생성 진행과 에디터 본문. 문항 확인 화면과 `POST /applications` 까지는 §9 에 들어왔고, 그 뒤의 진행 화면은 아직 자리표시자다([#184](https://github.com/Team-CareerCompass/CareerCompass-FE/issues/184)).
- 알림 목록과 설정. notification 모듈이 자리표시자다.
- For You 와 커리어 로드맵. foryou 모듈이 자리표시자다.
- 마이 탭의 나머지 화면. 마이 홈과 프로필 편집은 §8 의 「입력하기」 줄로 들어왔고, 경험 카드 목록과 과거 지원서 목록은 화면이 서 있지만 이 한 바퀴의 범위 밖이다. 지원서 등록은 아직 자리표시자다([#181](https://github.com/Team-CareerCompass/CareerCompass-FE/issues/181)).
- 내 게시판 목록. 화면은 있으나 §7 에 적은 대로 갈 길이 없다.
- 끊김 경로 전반(오프라인 스냅샷, 503, 토큰 재발급). [#265](https://github.com/Team-CareerCompass/CareerCompass-FE/issues/265)
  의 별도 항목이라 대본에는 각 절의 마지막 줄로만 걸어 두었다. 한 바퀴를 통과시킨 뒤에 따로 돈다.
