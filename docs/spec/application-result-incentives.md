# 지원 결과 입력 유인과 초기 코호트 운영

[FE #419](https://github.com/Team-CareerCompass/CareerCompass-FE/issues/419)의 네 가지 제품 결정을 기록한다. 결정일은 2026-09-21이다. 입력 유인의 효과가 검증되었다거나 실제 표본을 확보했다는 뜻은 아니다. 이 문서는 화면과 서버의 구현 완료를 대신하지 않는다.

## 결정 요약

| 결정할 것 | 현행 범위에서의 결정 |
| --- | --- |
| 입력할 이유 | 기존 지원 이력을 개인 회고 기록으로 쓰는 가치와, 결과 입력 화면에서의 짧은 안내를 채택한다. 입력 여부로 비교 열람을 잠그지 않는다. 결과 확인 푸시와 결과 Export는 채택하지 않는다. |
| 금전 보상과 검증 | 쿠폰 등 금전성 보상을 제공하지 않는다. 합격은 사용자가 직접 기록한 결과이며, 검증된 합격 실적으로 표시하지 않는다. |
| 초기 실제 표본과 첫 화면 | 같은 학과·학년의 소규모 자발적 참여자와 실제 합격 경험이 있는 참여자에게 자신의 실제 지원 이력을 기록하도록 안내한다. 집계 활용은 별도 동의가 확보된 기록으로 제한한다. 표본이 없거나 부족하면 비교를 비워 두고 개인 기록으로 돌아갈 수 있게 한다. 운영 집계에 시드나 합성 기록을 넣지 않는다. |
| 데모와 심사 | 실제 0표본 화면을 먼저 시연하고, 비교가 가능한 모습은 별도 발표 자료의 합성 예시로 설명한다. 예시임을 화면마다 표시하고 실제 사용자 수나 실측 성과로 말하지 않는다. |

## 현재 계약과 이번 결정의 경계

구현 근거의 우선순위는 [정본 안내](canon.md)를 따른다. 아래는 2026-09-21에 직접 확인한 계약과 연결 이슈다.

- [API_SPEC §6](https://github.com/Team-CareerCompass/CareerCompass-BE/blob/main/docs/API_SPEC_v0.1.md): `PATCH /applications/{id}/result`의 값은 `pending`·`pass`·`fail`·`none`이다. 미입력은 `none`이며 `null`을 새 값으로 보내지 않는다. `POST /applications/{id}/save`로 최종 저장할 때 이력이 생성되고, `GET /applications`는 지원 이력 목록이다.
- [FE #189](https://github.com/Team-CareerCompass/CareerCompass-FE/issues/189)가 참조하는 F4-4: 결과 입력은 선택 사항이며 나중에 입력하거나 수정할 수 있다. 모델 개선 활용은 사용자 동의 기반이다.
- [FE #188](https://github.com/Team-CareerCompass/CareerCompass-FE/issues/188): 목록에서 저장한 지원서, 공고, 분석 당시 적합도 점수 스냅샷과 결과를 확인한다. 목록 응답의 공고 정보 등 미확정 계약은 이 이슈의 기존 경계에 남는다.
- [API_SPEC §7](https://github.com/Team-CareerCompass/CareerCompass-BE/blob/main/docs/API_SPEC_v0.1.md)과 [BE #42](https://github.com/Team-CareerCompass/CareerCompass-BE/issues/42): `peer`·`senior`·`me_only` 코호트, `sampleSize`·`metrics`·`suggestions`가 있다. `senior`의 원천은 지원 이력의 `pass`이며 동의 기반 활용과 최소 표본 규칙이 필요하다.
- [BE #48](https://github.com/Team-CareerCompass/CareerCompass-BE/issues/48): 동의 저장·철회·보관 기간의 결정과 강제는 서버 담당 범위다. 이 문서는 그 절차가 이미 구현되었다고 가정하지 않는다.
- API_SPEC §7의 Export 요청에는 지원 결과 section이 없고, §8 알림 설정에는 결과 확인 유형이 없다. 기존 키의 의미를 바꾸거나 새 필드를 추측해 보내지 않는다.

이 문서의 새 결정은 입력 유인, 보상 비채택, 초기 운영, 발표 방식에 한정한다. 최소 표본 수, 부족 상태의 응답 형태, 코호트 집계 단위, 동의 목적·저장·철회 계약은 BE #42·#48의 결정을 기다린다. FE가 숫자나 DTO를 먼저 정하지 않는다.

## 1. 개인 기록의 가치와 입력 마찰 축소

입력자에게 주는 가치는 "어떤 지원서로 어디에 지원했고 결과가 어땠는지 다시 찾을 수 있음"이다. 기존 이력 목록과 저장된 지원서 열람을 활용한다. 합격과 불합격 모두 회고 기록으로 같은 가치를 갖도록 안내하며, 새 AI 회고 보고서·성공 확률·인과 분석을 약속하지 않는다.

| 후보 | 채택 여부와 이유 |
| --- | --- |
| 상호주의: 입력한 사람만 비교 열람 | 비채택. 첫 사용자에게 없는 결과를 요구하고, 기능을 열기 위한 임의 입력을 유도할 수 있다. 결과 입력이나 집계 동의를 비교 열람의 대가로 삼지 않는다. |
| 마찰 축소 | 기존 입력 흐름 안에서 채택. 선택 사항임을 알리고 기존 네 결과를 쉽게 고르게 한다. 결과 확인 푸시, 마감일 기반 자동 결과 추정, 일괄 갱신 기능은 추가하지 않는다. |
| 입력자 본인에게 남는 산출물 | 기존 지원 이력의 회고 가치를 채택. 현재 목록·지원서 열람을 사용하고 새 결과 Export나 집계 보고서를 약속하지 않는다. |
| 쿠폰 등 금전성 보상 | 비채택. 현재 진위 검증 수단이 없고, 보상 자격을 위한 허위 입력과 증빙 수집 운영이 새로 생긴다. |

지원 결과 입력 화면의 안내 문구는 다음과 같다.

> 결과를 기록하면 지원 이력에서 지원서와 결과를 함께 돌아볼 수 있어요. 입력은 선택 사항이며 나중에 바꿀 수 있어요.

기존 결과 선택지의 의미는 대기(`pending`), 합격(`pass`), 불합격(`fail`), 미입력(`none`)으로 유지한다. 안내를 닫거나 화면을 나가면 값을 자동 저장하지 않는다. 대기와 미입력을 합격·불합격으로 추정하지 않으며, 지원 마감일을 결과 발표일로 해석하지 않는다. 결과 변경의 저장 성공·실패 표시는 #189의 기존 입력 흐름에서 다룬다.

개인 결과 기록과 다른 사용자 비교·모델 개선 활용 동의는 별개의 선택이다. 기록했다고 자동 동의한 것으로 처리하지 않는다. 동의하지 않아도 개인 기록을 열람·수정하고, 공개 가능한 코호트 비교를 볼 수 있어야 한다. 동의 목적과 표현, 저장·철회 방식은 BE #48의 확정 문서에 맞춘다. 계약이 없는데 동의 완료라고 안내하는 UI는 만들지 않는다.

입력률 상승은 아직 가설이다. 첫 자발적 참여자의 사용 점검에서는 결과를 남겼는지, 안내의 개인적 이득을 이해했는지, 미입력·수정 경로를 찾았는지를 확인한다. 기존에 허용된 집계만 사용하며, 이 문서를 근거로 새 행동 로그나 원문 수집을 추가하지 않는다. 효과가 없으면 유인 정책을 다시 검토하되 쿠폰이나 접근 잠금으로 자동 전환하지 않는다.

## 2. 금전 보상과 합격 검증

이번 범위에서는 금전 보상과 보상용 합격 증빙 수집을 하지 않는다. 이메일·합격 통지서 업로드, 운영자 심사, 보상 자격 필드도 만들지 않는다. 진위가 검증되지 않은 결과는 자기 기록 및 동의한 집계의 재료로만 취급한다.

합격 선배 비교에는 "사용자가 직접 기록한 합격 결과를 바탕으로 한 비교예요"라는 출처 안내를 둔다. 이 값이 검증된 합격 인증이나 전체 학생의 대표 통계, 합격을 보장하는 기준으로 읽히지 않도록 한다. 같은 사람이 합격 이력을 여러 개 남겼을 때의 중복 처리와 `sampleSize`의 단위는 BE #42가 정한다. FE가 지원서 건수를 사람 수로 바꾸어 표시하지 않는다.

보상 정책을 나중에 바꾸려면 먼저 검증 근거, 수집할 증빙의 최소 범위, 심사 책임, 비용, 보관·삭제 조건과 부정 입력 대응을 결정해야 한다. 지금 그 구현을 후속 작업으로 예약하지 않는다.

## 3. 초기 실제 표본과 첫 사용자 경험

운영 표본은 실제 사용자가 자신의 계정에 남긴 실제 기록에서만 시작한다. 초기에 한 학과·학년의 자발적 참여자를 대상으로 개인 지원 이력을 써 보도록 안내하고, 해당 모집 범위의 실제 합격 경험자에게도 같은 방식으로 참여를 안내한다. 합격자만 모집해서 전체 사용자 집단을 대표한다고 해석하지 않는다. 합격 결과를 만들거나 실제보다 경험 수를 늘려 입력하도록 요청하지 않는다.

다른 사용자 비교에 쓰는 기록은 BE #48에서 정한 동의와 BE #42의 코호트 적격성·집계 규칙을 충족해야 한다. 해당 계약과 적용이 준비되기 전에는 집계 목적으로 데이터를 모으거나 기존 개인 기록을 일괄 편입하지 않는다. 참여 안내·동의 확인·집계 가능 여부 확인 순서로 운영하며, 참여 인원과 표본 확보를 이 문서의 완료 실적으로 보고하지 않는다.

실제 표본 모집과 동의 운영의 책임은 플랫폼 운영 담당, 집계 적격성 판정의 책임은 BE #42·#48 담당이다. 모집 대상의 연락처나 확정 참여자는 현재 정해져 있지 않다. 정해진 모집 인원이나 심사 일정에 맞추려고 최소 표본 규칙을 낮추지 않는다.

| 실제 상태 | 사용자에게 보여 줄 것 | 다음 행동 |
| --- | --- | --- |
| 개인 지원 이력 0개 | "공고에서 지원서를 만들고 저장하면 이력이 여기에 쌓여요." | 기존 공고·초안 작성 흐름으로 안내한다. 결과 입력을 먼저 요구하지 않는다. |
| 개인 이력 있음, 결과 미입력 | 저장된 지원서와 현재 결과 상태, 위 개인 기록 안내 | 기존 결과 입력 화면에서 선택적으로 기록한다. |
| `peer` 또는 `senior` 비교 표본 없음·최소 기준 미달 | "비교할 데이터가 아직 충분하지 않아요. 내 기록을 먼저 확인해 보세요." | 지원 이력 또는 기존 개인 기록 경로로 이동한다. 평균 막대를 0으로 그리거나 합성 평균으로 채우지 않는다. |
| 비교 가능한 실제 코호트 | 서버가 공개를 허용한 비교 값, `sampleSize`, 자기보고 출처 안내 | 개인 기록과 코호트 비교를 구분해 본다. |
| `me_only`의 개인 데이터 부족 | 개인 데이터 부족 안내 | 경험·프로필 입력 등 기존 개인 기록 흐름을 안내한다. 표본 부족한 `peer`·`senior`를 임의로 `me_only` 응답처럼 바꾸지 않는다. |
| 요청 실패 | 기존 오류·재시도 화면 | 표본 부족으로 단정하지 않는다. |

표본 0과 최소 기준 미달은 같은 안전한 안내를 사용할 수 있다. 내부적으로 상태를 구분할지, 적은 인원 수를 공개할지와 정확한 응답 의미는 BE #42가 확정한다. 예시 응답의 `sampleSize: 86`은 실제 표본이 아니며 최소 기준도 아니다. FE가 로컬 숫자로 공개 여부를 결정하지 않는다.

결과 수정·이력 삭제·활용 동의 철회 시 집계 반영 시점과 캐시 무효화는 BE #42·#48에서 함께 정한다. 이 문서는 즉시 반영 등 현재 없는 보장을 하지 않는다. 운영 시드는 쓰지 않으므로 데모 기록이나 팀의 가짜 합격이 실제 코호트에 섞일 이유가 없어야 한다.

## 4. 데모와 심사에서의 설명

발표는 실제 0표본 상태와 합성 비교 예시를 나눠 진행한다. 비교 예시는 앱의 운영 응답을 바꾸는 데모 모드로 만들지 않는다. 별도 슬라이드나 정적 목업에 아래 고지를 항상 포함한다.

> 합성 데이터로 만든 화면 예시입니다. 실제 사용자 통계가 아닙니다.

화면 일부를 캡처하거나 보고서에 옮겨도 고지가 함께 남아야 한다. 예시의 사용자 이름·학교·지원처는 가상의 값으로 쓰며 실제 사용자 원문을 복사하지 않는다. 숫자·평균·제안은 이해를 위한 예시이며 실험 결과나 실제 합격 기준으로 설명하지 않는다. API_SPEC의 예시를 재사용해도 같은 원칙을 적용한다.

발표 순서는 다음과 같다.

1. 실제 데이터로 운영 중인 버전과 확인 날짜를 밝힌다. 표본을 확보하지 못했다면 그대로 말한다.
2. 개인 지원 이력이 없는 상태를 보여 주고, 공고에서 지원서를 만들고 저장한 뒤 이력에서 다시 찾는 경로를 설명한다.
3. 기존 결과 입력 화면이 준비되면 합격·불합격·대기·미입력과 나중에 수정하는 흐름을 보여 준다. 아직 구현 전이면 해당 화면도 목업이라고 밝힌다.
4. 실제 비교의 표본 부족 화면을 보여 주고, 최소 표본 규칙 때문에 평균을 감춘다는 원칙을 설명한다. 구현 전이라면 표본 부족 화면 역시 정적 목업으로 표시한다.
5. 별도 합성 비교 예시로 `peer`와 `senior`의 두 막대, 표본 표시, 제안의 읽는 방법을 설명한다. 합성 예시를 실제 사용자가 축적한 데이터로 소개하지 않는다.
6. 실제 표본을 확보한 뒤에는 서버가 공개를 허용한 실제 비교를 보여 줄 수 있다. 실제 화면과 합성 예시를 전환할 때 출처를 다시 밝힌다.

발표 전 확인 목록:

- 실제 데이터 없음, 최소 기준 미달, 공개 가능한 비교, 요청 실패의 의미를 구별한다.
- 합성 예시의 고지가 모든 슬라이드·캡처에 보이며 실제 서비스에 합성 기록을 넣지 않았다.
- 동의 없는 기록이 비교 재료로 쓰이지 않는다는 근거를 BE #48의 확정 계약과 실행 결과로 확인한다. 아직 근거가 없으면 운영 검증 완료라고 발표하지 않는다.
- 실제 표본 수와 구현 완료 여부를 근거 없이 숫자로 채우지 않는다.
- 자기보고 결과의 한계와 입력 유인의 효과가 미검증임을 설명한다.

이 목록은 발표 운영 절차다. #419의 문서 작성 완료가 발표 자료 제작이나 실제 사용자 모집 완료를 뜻하지 않는다.

## 후속 구현과 전달 범위

기존에 열린 구현 이슈를 후속으로 사용한다. 아래 범위를 추적하기 위해 같은 기능의 새 이슈를 중복 등록하지 않는다. 다른 소유 모듈의 코드와 서버 계약은 이 문서 PR에서 변경하지 않는다.

| 후속 이슈 | 이 결정의 반영 범위 | 확인할 조건 |
| --- | --- | --- |
| [FE #188](https://github.com/Team-CareerCompass/CareerCompass-FE/issues/188) | 기존 지원 이력을 개인 회고 기록으로 사용, 이력 0개 안내 | 분석 당시 점수와 현재 점수를 혼동하지 않고 저장한 지원서와 결과를 다시 찾을 수 있다. |

이 표는 구현 책임과 전달할 결정의 경계를 나타낸다. 단순 관련 링크를 GitHub `blocked_by`가 설정된 것으로 해석하지 않는다. 기존 구현의 의존 관계는 각 담당자가 실제 계약과 함께 확인한다. 결과 알림·보상·새 회고/Export 기능의 구현 예약은 남기지 않는다.
